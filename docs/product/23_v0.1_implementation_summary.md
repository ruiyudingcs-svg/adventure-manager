# V0.1 功能实现总结

状态：Feature Complete / Release Validation

最后更新：2026-07-26

## 1. 当前结论

`docs/product/01_v0.1_product_spec.md` 定义的 V0.1 功能范围已经实现。玩家可以从新战役开始，
在 Dashboard 阅读局势与信箱，比较合同，选择四人小队、补给和行动倾向，查看稳定预测，
提交不可逆计划，推进周流程，阅读四阶段结算及组织/世界变化，保存并继续游戏，最终进入
四种结局之一。

当前不再增加 V0.1 功能。项目进入 Release Validation：完成 Windows 导出环境验证、
三种目标分辨率和键盘操作检查，以及不依赖开发者说明的完整新玩家整局。

## 2. 已实现的纵向切片

### 管理循环

- 新游戏由唯一 `CampaignSetupDefinition` 确定性建立，并通过真实周流程进入第 1 周。
- Dashboard 展示周次、资金、声望、世界局势、进度钟、合同栏、NPC 预告和信箱。
- Roster 展示八名成员的能力、疲劳、士气、伤势、可出勤状态及个人详情。
- Contract Planning 使用临时 draft；玩家必须选择四名可用成员，并可配置补给和
  Approach。英雄卡显示六项能力，便于比较人选。
- `ContractForecastService` 使用 64 个稳定样本复用正式 Resolver，不消费锁定结算 seed。
- 提交后锁定计划与结果；Resolution 按四阶段、成员、工会与世界、原因日志展示已提交结果，
  UI 刷新不会重新投掷。
- 玩家可以接取、拒绝或跳过合同，连续推进 10—15 周并进入稳定结局。

### 领域模拟

- 合同使用固定四阶段、显式 `MissionContext`、独立随机流和结构化原因记录。
- 能力、协同、疲劳、伤势、Approach、补给、条款、报酬和 outcome profile 由同一
  通用 Resolver 处理，不使用合同专用运行时代码。
- 世界侧包含周维护、问题生命周期、五条进度钟、阵营两遍规划、行动承诺、合同到期、
  NPC 完成、跨钟触发和稳定结局选择。
- 所有有意义的状态修改通过 `StateOperation` 和原子 `CampaignTransaction` 提交；
  Definition 在运行时保持只读。
- 所有模拟随机均来自显式 seed，同一输入和玩家策略可复现完整战役 signature。

### UI、存档与错误处理

- Control-based Football Manager 风格应用壳已经覆盖 Dashboard、Roster、
  Contract Planning、Resolution 和 Ending。
- 信箱及成员按钮的信号生命周期问题已经修复；动态节点不会在自身 `pressed` 调用栈内释放。
- 合同来源、结算阶段、状态字段和原因日志已补齐中文投影，不再向玩家暴露
  `[MISSING:...]`、格式模板或内部序列化签名。
- 六步引导是会话级状态，可跳过且不修改存档 schema。
- schema v1 planning-only JSON 存档支持 canonical state、加载验证、原子替换和
  `.bak` 恢复候选。保存、继续加载和第二周结算已经手工确认。
- Catalog/setup、存档、空消息、非法计划、事务失败和已结束战役均有显式反馈。

## 4. 架构边界

- 引擎与语言：Godot 4.7 stable、静态类型 GDScript。
- UI 不保存游戏公式，不直接协调多对象状态修改；领域模拟可脱离场景树运行。
- Autoload 只有 `DataCatalog`、`GameSession`、`SceneRouter`；`SaveService` 是普通
  `RefCounted`。
- V0.1 没有第三方 addon、全局事件总线、可执行字符串规则或额外存档 schema。
- 当前数值权威来源仍是 Accepted 规则文档；本总结只记录实现状态，不覆盖产品和规则。

## 5. 验证与平衡证据

- 最近一次完整 Godot 4.7 headless suite：**233 passed、0 failed**。
- 四条从真实新游戏开始的定向 ending path：4 passed、0 failed。
- 十局真实 `GameSession` 自动战役：全部在第 10—15 周结束；每局至少完成一次
  planning 保存/加载，同 seed 和策略可复现。
- 经人工批准，单次 check 等级边界调整为 `70/50/30/10`；合同加权等级边界保持
  `80/60/40/20`。相关 Accepted 规则、golden 和测试已经同步。
- 首周最佳准备方案的 64-sample 精确结果：
  - 定位巨龙巢穴：1 Failure、37 Partial、26 Success。
  - 回收完整尸体：14 Failure、50 Partial、0 Success。

- 十局自然策略报告仍偏向 Failure，因为该简单自动玩家不读取六项能力或条款；
  这被记录为策略局限，没有继续整体降低合同难度。

## 6. 运行与测试

在 Godot 4.7 stable 编辑器中打开项目根目录并运行项目即可进入应用壳。命令行完整测试：

```bash
godot --headless --path . --script res://tests/run_all.gd
```

当前开发机确认使用 `4.7.stable.official.5b4e0cb0f`。若 `godot` 不在 `PATH`，使用
`D:\software\Godot\Godot_v4.7-stable_win64` 下的 console 可执行文件运行同一参数。

## 7. 剩余发布验收

以下项目尚未通过，不应写成已完成：

1. 安装 Godot 4.7 stable Windows export templates。
2. 生成并启动 Windows Debug 与 Release 构建，在导出构建中完成至少两周。
3. 人工检查 1280×720、1600×900、1920×1080 下的完整可读性与交互。
4. 人工确认键盘焦点、Enter/Escape 和核心流程。
5. 由未阅读开发文档的新玩家完成一局。
6. 后续清理测试退出时的 `ObjectDB` 实例与 38 个资源占用警告。警告当前不影响
   测试退出码，但属于测试基础设施风险。

Windows preset 已存在；当前导出失败的已知原因是本机缺少
`4.7.stable/windows_debug_x86_64.exe` 和 `windows_release_x86_64.exe` 模板，而不是
项目功能或导出配置被验证为失败。

## 8. 后续变更边界

发布验收前只接受阻断 bug、可访问性问题、文案错误和必要的范围内平衡修正。新合同、
新成员、新阵营、新局势、战斗表现、在线功能或其他 V0.2 系统，应先单独评估产品范围，
不得借“收尾”进入 V0.1。

试玩反馈暴露出的可控性问题、6 选 1 合同组合、招募/临时补员、英雄定位细分和战斗表现顺序，
已整理到 `docs/product/24_post_v0.1_agency_roadmap.md`。该文档当前是 Proposed planning，
不覆盖本总结或 V0.1 Accepted 规则。
