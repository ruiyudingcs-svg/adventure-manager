状态：路线已定义；仅 Task 001—004 已展开为任务书

## 1. 用途

本文件只负责实现顺序、依赖和阶段门，不替代 `docs/` 中的产品与规则文档。执行具体任务时仍必须读取根目录 `AGENTS.md`、相关设计文档和对应任务书。

采用“完整路线骨架 + 近期任务细化”的方式：

- 先列出 V0.1 的完整关键路径，避免局部实现走向错误方向。
- Task 001—004 提供可审查的详细任务书。
- 后续任务只保留目标、依赖和退出条件；到达阶段门后，再根据真实 API 和测试结果细化下一组。
- 不允许一次让 Codex 连续执行整个里程碑。

## 2. 当前阶段门

### Gate A：合同评分的数值映射

Task 003 开始前，Accepted 文档必须补齐以下确定性规则：

- `cohesion_score` 如何转换为 `cohesion_modifier`。
- `cohesion_score` 所需的关系、纪律支持和冲突输入如何从四人队确定性汇总。
- 成员疲劳如何转换为队伍或判定级 `fatigue_penalty`。
- 成员伤势如何转换为 `injury_penalty`。
- `seeded_variance` 的精确整数/浮点分布、闭区间和判定前精度/舍入规则。

现有文档只声明了评分项，没有给出这三项的数值映射。实现者不得自行发明临时公式或把它们永久设为零。

### Gate B：认可度与伤病结算

Task 004 开始前，Accepted 文档必须补齐：

- 性格、禁忌与 method tag 之间的 `method_fit` 表或等价白名单规则。
- `personal_fit` 各来源的明确数值规则。
- 公开条款如何进入任务前预期认可度，且不与合同意图重复计分。
- 合同风险、结果风险、当前疲劳、保护与补给如何汇总为轻伤/重伤概率。
- 每名成员的确定性伤病投掷、轻伤/重伤阈值和恢复结果。
- `fatigue_multiplier` 的应用顺序和舍入规则。
- 消除 `人员安全条款读取重伤数量 → 条款可能封顶最终 tier → ContractOutcomeTable 的 injury_risk_modifier 又依赖最终 tier` 的循环，并明确伤病、条款和最终结果表的唯一结算顺序。

已定案的 Approach 重伤乘数、任务后价值评价、条款和报酬规则可以直接实现；上述缺口不能靠测试 fixture 暗中固化。

## 4. 分批细化节点

### 第一批：Task 001—004

先证明项目骨架、确定性基础和合同结算边界。Task 004 通过后，合同领域的公开类型才视为稳定。

### 第二批：Task 005—008

在 Task 004 的真实 API 上细化数据目录、内容验证、状态事务和局势服务。不要在 Task 004 之前为 `.tres` 猜测最终字段布局。

### 第三批：Task 009—013

在局势与状态事务稳定后细化合同生成、阵营行动、周流程、消息和完整剧本内容。

### 第四批：Task 014—017

领域循环能 headless 完整运行后才细化 UI、存档、平衡和导出。

## 5. 每个任务的统一执行规则

1. 开始前读取根目录 `AGENTS.md`、任务书列出的权威文档和现有测试。
2. 若权威文档缺少任务所需公式或彼此冲突，先报告阻塞；不得把猜测写成生产规则。
3. 只修改任务书允许的文件。需要扩大范围时先停止并说明原因。
4. 新规则必须有 focused test；确定性逻辑必须重复相同输入和 seed。
5. 先运行 focused tests，再运行完整命令：

```bash
godot --headless --path . --script res://tests/run_all.gd
```

6. 不自动更新 golden 期望；差异交给人工确认。
7. 完成后检查：范围膨胀、共享 Resource 被修改、UI 含公式、全局随机数、无原因状态变化。
8. 报告实际修改文件、行为、测试命令与结果、假设和剩余风险。未运行的测试不得声称通过。
